Flink SQL 撤回失败排查记录：更新键丢失与动态字段

zcyoop 发表于 10-122026-10-12T00:00:00+08:00
更新于 10-122026-10-12T17:13:48+08:00 15 分钟 阅读

一、问题背景

Flink SQL 的统计结果会随着源数据变化而更新，不是只向数据库追加新记录。

例如，一笔 30 元订单从支付方式发生了变化，正确场景如下：

1
2
3
4

记录旧支付方式统计
撤回旧分类的统计
写入新分类的统计
最终只保留一笔、30 元

如果旧统计没有正确撤回，就可能变成：

支付分类笔数金额
旧分类，错误残留130
新分类130
合计260

那为什么会撤回失败就是本文要探究的问题

二、基本概念

2.1 Flink SQL 传递的是变更流

Flink 用 RowKind 表示消息含义：

类型标记含义
INSERT+I新增结果
UPDATE_BEFORE-U更新前的旧结果
UPDATE_AFTER+U更新后的新结果
DELETE-D删除结果

例如，一组金额从 30 变成 50，可以通过撤回旧结果、写入新结果来表达。

具体输出哪些变更类型，取决于执行计划和下游能力，不是每次更新都必须产生四种消息。

2.2 inputUpsertKey（更新键）标识的是结果的身份字段

以聚合为例：

1
2
3
4
5
6
7
8

SELECT
    uuid,
    storeId,
    tradeDate,
    pmSign,
    SUM(amount) AS saleAmt
FROM orders
GROUP BY storeId, tradeDate, pmSign

同一个“门店 + 日期 + 支付分类”只有一条当前聚合结果，因此规划器能够推导：

1

更新键 = storeId + tradeDate + pmSign

金额可以从 30 变成 50，但仍是同一组统计，所以金额不属于这条结果的身份。

如果最终输出字段为：

1
2
3
4
5

0：uuid
1：storeId
2：tradeDate
3：pmSign
4：saleAmt

对应配置就是：

1

inputUpsertKey=[1,2,3]

这里记录的是字段位置，不是额外生成一个数据 ID。规划时决定使用哪些字段，运行时比较这些字段的值。

其他 SQL，例如 JOIN、窗口和去重，有各自的键推导规则，不是所有查询都直接取 GROUP BY。

2.3 Sink 主键与输入更新键的功能差异

键本例作用
Sink 主键uuid最终操作结果表的哪条记录
输入更新键storeId + tradeDate + pmSign上游哪条结果正在更新或撤回

SinkUpsertMaterializer 的状态可以理解为：

1
2

先按 Sink 主键找到状态桶
再在桶内匹配需要更新或撤回的输入记录

一般情况下，同一个 Sink 主键可能对应不同的上游输入结果，因此不能把每一条撤回都无条件翻译成“删除数据库这个主键”。算子需要先确定撤回的是哪条输入，以及撤回后是否还有有效结果。

本例希望 UUID 与完整分组一一对应，但规划器不会自动证明 MD5(CONCAT(...)) 能够唯一代表全部分组。

目标表声明 PRIMARY KEY (uuid) NOT ENFORCED，也不等于上游计算表达式的唯一性已经得到证明。NOT ENFORCED 表示 Flink 不主动检查该约束；数据库的物理主键是另一个层面。

三、产生原因之一：更新键在 SELECT 中没有成功传递

注意：“更新键在 SELECT 中没有成功传递”只是导致FlinkSQL从更新键判断退回到整行匹配

3.1 不是 SELECT 与 GROUP BY 字段不一样，就一定丢失

准确判断标准是：

经过最终 SELECT 后，规划器是否还能确认至少一组输出字段能够唯一识别上游结果。

例如：

1
2
3
4
5
6
7

SELECT
    storeId,
    pmSign,
    SUM(amount) AS saleAmt,
    COUNT(*) AS orderNum
FROM orders
GROUP BY storeId, pmSign

SELECT 比 GROUP BY 多了金额和笔数，但完整分组键仍然保留，因此可以继续识别 storeId + pmSign。

3.2 哪些情况可能丢失？

情况 A：没有输出完整分组键

1
2
3

SELECT storeId, SUM(amount) AS saleAmt
FROM orders
GROUP BY storeId, pmSign

上游按“门店 + 支付分类”分组，最终只输出门店。仅凭门店不能区分不同支付分类，因此原来的完整分组键不能继续传递。

如果没有其他可推导的更新键，就会没有可用的 inputUpsertKey。

情况 B：计算使不同分组可能产生相同输出

1
2
3

SELECT storeId, UPPER(pmSign) AS pmSign, SUM(amount) AS saleAmt
FROM orders
GROUP BY storeId, pmSign

原来的 abc 和 ABC 是不同分组，转换后都可能输出 ABC。计算后的字段不一定能唯一识别原分组。

情况 C：值没有变化，但规划器无法识别字段映射

本次嵌套 CAST 属于这一类：日期值没有改变，完整分组也没有改变，但规划器未能传递日期的更新键信息。

因此，不能简单归结为 SELECT 与 GROUP BY 的业务语义不一致。

四、产生原因之二：整行匹配遇到动态字段

4.1 更新键丢失后如何匹配？

在本次实际存在的 SinkUpsertMaterializer 中：

1
2

有 inputUpsertKey：比较指定的更新键字段
没有 inputUpsertKey：比较整行，忽略 RowKind

忽略 RowKind，是因为保存的旧结果可能是 INSERT，到达的撤回可能是 DELETE，它们的变更类型不同，但可能对应同一条业务结果。

不是每个作业都需要这个算子；本文讨论的是规划器实际生成了该算子的链路。

4.2 撤回不一定是最终旧行的原样副本

举例如下

最终 SELECT 包含：

1

CURRENT_TIMESTAMP AS modifyDate

处理链路：

1
2
3
4
5
6
7

聚合产生业务结果或撤回
    ↓
最终 SELECT 计算 UUID、modifyDate 等
    ↓
materializer
    ↓
Sink

第一次输出：

1
2
3

聚合结果：金额30
SELECT 在 10:00:01 处理
最终旧行：金额30，modifyDate=10:00:01

随后撤回：

1
2
3

聚合产生旧业务结果的撤回：金额30
SELECT 在 10:00:02 再处理
最终撤回行（重新计算日期）：金额30，modifyDate=10:00:02

同一份旧业务内容再次经过 SELECT，动态字段会在这次处理时重新计算，导致撤回的消息和原始消息不匹配，最终导致撤销失败

4.3 匹配失败为什么会留下旧统计？

Flink 1.17.2 的 retractRow 中，找不到匹配行时直接返回：

1
2
3
4
5

final int index = findFirst(values, retract);
if (index == -1) {
    LOG.info(STATE_CLEARED_WARN_MSG);
    return;
}

后续移除状态、发送删除的逻辑没有执行。

1
2
3
4
5
6
7

撤回已到达 materializer
    ↓
没有匹配到旧行
    ↓
没有向 Sink 发送删除
    ↓
旧分类残留

这不是数据库主键删除失败，而是删除没有继续发出去。

该分支的日志会提示状态 TTL，但本例保留 48 小时 TTL、几秒内复现，不能仅凭提示认定状态真的过期。
